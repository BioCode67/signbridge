# KOREN AI Cloud (CHEETAH) 운영 가이드

첨부해 주신 워크스페이스 생성 화면 기준으로, SignBridge 학습을 이 환경에서 돌리기 위한
설정·순서·주의점을 정리한다.

---

## 0. 가장 먼저 고쳐야 할 것 — **볼륨 1 GiB**

생성 화면의 볼륨 목록에 `Home / 1 GiB / /home/jovyan (CEPH)` 하나만 잡혀 있다.
**이 상태로는 AI Hub 데이터를 한 조각도 받을 수 없다.** 워크스페이스를 만들기 전에
[볼륨/모델/데이터셋 추가]로 **데이터용 볼륨을 따로 붙여야 한다.**

### 용량 산정

| 대상 | 크기 감각 | 메모 |
|---|---|---|
| 원본 영상(「수어 영상」 53만 클립 × 5각도) | **TB급** | 전량 내려받지 말 것 |
| 키포인트 JSON (원본) | 수십~수백 GB | JSON은 부피가 매우 크다 |
| **랜드마크 팩(.npz, 이 파이프라인 산출물)** | **프레임당 ≈0.5KB** | 30fps 1시간 ≈ 54MB |
| 체크포인트 | 실행당 수십 MB | 모델이 3~6M 파라미터로 작다 |

팩 기준으로 계산하면, **48M 프레임(≈450시간 분량)이라도 약 25GB**다.
부피를 차지하는 건 언제나 **원본**이지 학습 데이터가 아니다.

> **1 GiB로는 `pip install`조차 실패한다.** `mediapipe` + `opencv` + `onnxruntime`만 해도
> 1 GB를 넘는다. 홈 볼륨은 데이터가 아니라 **패키지 때문에** 늘려야 한다.
> 생성 화면 볼륨 표의 **[볼륨조정]** 버튼으로 Home을 먼저 키울 것.

> 🔴 **홈 볼륨은 워크스페이스를 삭제하면 함께 삭제된다**(Cheetah 사용자 매뉴얼 명시).
> 코드·체크포인트·팩을 홈에 두면 워크스페이스를 다시 만드는 순간 전부 사라진다.
> **저장소 clone부터 사용자 볼륨에 할 것.** 홈은 pip 패키지 전용으로만 쓴다.
>
> 매뉴얼은 한 가지를 더 경고한다 — 볼륨으로 등록되지 않은 경로(`/`, `/home/` 등)에 둔
> 파일은 **워크스페이스 중지나 Pod 재생성만으로도** 사라진다. 데이터는 반드시 연결된
> 볼륨 경로 안에 둘 것.

### 권장 볼륨 구성 (쿼터 상한 900 GiB 기준)

볼륨 생성 화면의 신청 용량 슬라이더 상한이 **900 GiB**다. 「수어 영상」 원본 영상 전량(TB급)은
애초에 들어가지 않으므로, **원본을 쌓아 두는 게 아니라 흘려보내는** 구성으로 간다.

| 볼륨 이름 | 볼륨 경로 | 용량 | 용도 |
|---|---|---|---|
| Home (기존) | `/home/jovyan` | **50 GiB**로 상향 | **pip 패키지 전용** (삭제돼도 되는 것만) |
| `SignBridge 데이터` | `sbdata` | **150 GiB** | 저장소 clone · 팩 · 사전 · 체크포인트 — **영구 보관** |
| `SignBridge 원본` | `sbraw` | **600 GiB** | AI Hub 원본 **임시 작업 공간** — 팩 만든 뒤 비운다 |

합계 800 GiB로 100 GiB 여유를 남긴다.

> 슬라이더 상한 900 GiB는 **그룹 관리자가 정한 현재 쿼터**이지 물리적 한계가 아니다.
> 소개서 기준 스토리지는 **전체 15TB**이고 "최대 15TB 내에서 할당 가능"이라고 되어 있다.
> 나중에 모자라면 `자원 요청`으로 증설을 신청할 수 있다.

> ⚠️ **볼륨 경로는 파일시스템 경로가 아니다.** 입력 규칙이 "영문 대소문자·숫자·`-`·`_`,
> 4~24자"라 `/data/raw` 같은 슬래시 경로를 넣을 수 없다. `sbdata` 같은 **식별자**를 넣고,
> **생성 후 워크스페이스 볼륨 표에 표시되는 실제 마운트 경로를 확인**해서 그 값을
> `DATA_ROOT`·`RAW_ROOT`로 넘긴다(잡 스크립트가 전부 환경변수라 경로가 무엇이든 상관없다).
>
> **볼륨 경로는 생성 후 변경 불가**이므로 이름을 신중히 정할 것.

### 원본 600 GiB로 TB급 데이터를 처리하는 법 — 배치 후 삭제

팩은 **프레임당 ≈0.5KB**로 원본 영상의 수천 분의 일이다. 그래서 원본을 전부 보관할 필요가 없다.

```
① sbraw에 원본 일부(예: 200 GiB) 다운로드
② extract_mediapipe.py --resume 로 팩 생성 (sbdata에 누적)
③ sbraw의 처리 끝난 원본 삭제
④ ①로 돌아가 다음 묶음
```

`--resume`이 이미 만든 팩을 건너뛰므로 몇 번을 반복해도 안전하다.
이 방식이면 **600 GiB 작업 공간으로 수 TB 분량을 통과**시킬 수 있고, 남는 건 수십 GB짜리 팩뿐이다.

> **컨테이너는 휘발성이다.** 워크스페이스가 재시작되면 볼륨 밖의 모든 것이 사라진다.
> 체크포인트 출력(`--out`)은 반드시 마운트된 볼륨 경로로 줄 것.

### 단계적 접근 (권장)

1. **1단계 — 재난 수어 데이터, 형태소 JSON만.**
   키포인트가 형태소 JSON의 `landmarks`에 이미 들어 있으므로(README의 함정 표 참고)
   **영상을 안 받아도 학습을 시작할 수 있다.** 용량이 작아 900 GiB 안에서 여유롭고,
   여기서 파이프라인을 완주해 첫 정확도 숫자를 만든다.
2. **2단계 — 도메인 갭이 문제가 될 때만 영상 재추출.** 1단계 결과가 웹캠에서 잘 안 되면
   그때 재난 데이터 영상만 받아 MediaPipe로 재추출한다(위 배치 방식).
3. **3단계 — 「수어 영상」 표본으로 사전학습.** 53만 클립 전량이 아니라 각도 1~2개로
   샘플링한다. 사전학습에는 그것으로 충분하다.

**영상부터 받지 말 것.** 1단계가 가장 싸고 가장 빠르게 "실제로 학습되는가"를 알려 준다.

## 0-1. 자원은 "신청 → 관리자 승인 → 할당" 이다

워크스페이스 생성 화면에서 **CPU** 탭을 고르면
`CPU 타입으로 할당된 자원이 없습니다`가 뜰 수 있다. 버그가 아니다.

Cheetah 매뉴얼은 자원 항목을 "**할당 받은** 자원 종류 선택 — GPU 또는 CPU"라고 적고 있다.
즉 **계정에 미리 배정된 자원만 고를 수 있다.** KOREN 소개서의 절차도 마찬가지다.

```
자원 사용 규모 요청  →  관리자 승인  →  운영자가 사용자에게 할당
```

기본 상태에서는 GPU(`h200-mig-1g.35gb` ×1)만 배정돼 있고 **CPU 타입은 배정돼 있지 않다.**

**단, `자원 요청` 화면으로 스스로 해결되지 않을 수 있다.** 요청 팝업의 리소스 드롭다운에는
**그룹에 등록된 자원 유형만** 나온다. 현재는 `[GPU] h200-mig-1g.35gb` 하나뿐이고,
CPU Core·메모리 슬라이더는 "리소스 유형이 CPU인 경우에만 설정할 수 있습니다"라는 안내와 함께
`0 core / NaN`으로 비활성이다. **목록에 없는 유형은 신청 자체가 불가능하다.**

즉 이건 "AI Cloud는 GPU만 준다"는 뜻이 아니라 **이 그룹에 CPU Pod 유형이 아직 등록되지
않았다**는 뜻이다(제공 안내문에도 "GPU 및 CPU Pod 자원 활용" 교육 항목이 있다).
→ **운영 담당자에게 CPU Pod 자원 등록을 요청**해야 한다.

| 참고 | 값 |
|---|---|
| 상세 매뉴얼 | `http://116.89.177.100:8080/cheetah-document/v2.6/index.html` (또는 `COMMUNITY → Documents`) |
| 운영 문의 | `jilee@jininfra.com` |
| 추가 GPU | 소개서 Case3에 **H200 35GB MIG ×6** 구성 예시가 있다. 병렬 실험이 필요하면 증설 신청 가능 |

### CPU 자원이 없어도 막히지 않는다 — 두 가지 이유

1. **GPU 워크스페이스에 vCPU 16 · 메모리 128 GiB가 이미 딸려 온다.** MediaPipe 추출을
   여기서 돌려도 속도는 같다. 손해는 그동안 GPU가 노는 것뿐이다(§1 참고).
2. **1단계는 애초에 추출이 필요 없다.** 키포인트가 형태소 JSON에 이미 들어 있으므로
   대량 CPU 작업 없이 학습까지 갈 수 있다.

그래서 순서를 이렇게 잡으면 대기 시간이 0이다.

1. 지금 → GPU 워크스페이스에서 스모크 테스트 + 형태소 JSON ETL + 첫 학습
2. 그 사이 운영 담당자에게 CPU Pod 자원 등록 요청
3. 등록되면 → CPU 워크스페이스로 추출을 옮겨 GPU를 놀리지 않게 한다 (선택)

## 1. GPU 워크스페이스 하나로도 전부 된다

CPU 자원이 등록돼 있지 않아도 파이프라인은 막히지 않는다. **GPU 워크스페이스에 이미
vCPU 16 · 메모리 128 GiB가 함께 붙어 나오기 때문**이다(생성 화면의 자원 카드에 표시된다).
MediaPipe 추출도 이 16 vCPU로 그대로 돌릴 수 있다.

즉 CPU 워크스페이스 분리는 **필수가 아니라 최적화**다. 유일한 손해는 며칠 걸리는 추출 동안
GPU가 놀고 있다는 것뿐이고, GPU 할당량이 1개라 어차피 그동안 다른 학습을 돌릴 수도 없다.

| 상황 | 구성 |
|---|---|
| **CPU 자원 없음 (현재)** | GPU 워크스페이스 하나에서 ETL → 학습을 **순차 진행**. 문제없다 |
| CPU 자원이 등록되면 | `signbridge-etl`(CPU)에서 추출, `signbridge-train`(GPU)에서 학습. GPU를 놀리지 않는다 |

두 워크스페이스를 쓰게 되면 **같은 데이터 볼륨을 붙여** 작업을 이어간다.

> CEPH 볼륨이 **동시 마운트를 허용하지 않을 수 있다**(RWO). 그렇더라도 문제가 되지 않는다 —
> ETL이 끝나야 학습을 시작하므로 순서상 둘을 동시에 켤 일이 없다.

> 추출이 오래 걸리면 `--every 2`로 30fps → 15fps 다운샘플하면 시간이 절반이 된다.
> 수어 인식에는 대개 충분하다.

## 2. 워크스페이스 설정값

첨부 화면의 기본값이 대부분 그대로 좋다.

| 항목 | 값 | 비고 |
|---|---|---|
| 자원 | `h200-mig-1g.35gb` (학습) | vCPU 16 / Mem 128Gi |
| 이미지 | `cheetah/gpu workspace:ubuntu22.04-cuda12.4-cudnn` | 그대로 |
| 가상환경 | `torch2.5.1 py3.12 cuda12.4` | 그대로. **2.5.1에서 학습·내보내기 실행 검증 완료** |
| 볼륨 | 위 표대로 추가 | **반드시 변경** |

### MIG 슬라이스에서 알아 둘 것

- `nvidia-smi`에 MIG 디바이스로 보이고, **35GB 전부 쓸 수 있다.**
- 다만 연산은 **FP32 17.14 TFLOPS로 H200 전체(60 TFLOPS)의 약 29%**다(소개서 기준).
  메모리가 남는다고 모델을 키우면 느려지기만 한다.
  → 배치를 키워 처리량을 올리는 쪽이 이득이다(메모리는 남으므로).
- **bf16을 쓸 것**(Hopper 네이티브). 기본값이 `--amp bf16`이다.
  fp16의 손실 스케일링 불안정이 없다.
- MIG에서는 멀티 프로세스 GPU 공유가 제한된다. `--workers`(데이터로더)는 CPU 쪽이라 무관.

## 3. 초기 설정

```bash
# 코드는 홈이 아니라 **사용자 볼륨**에 둔다 (홈은 워크스페이스 삭제 시 함께 사라진다).
# <VOL>은 워크스페이스 볼륨 표에 표시된 sbdata의 실제 마운트 경로.
cd <VOL> && git clone https://github.com/BioCode67/signbridge.git app && cd app
git checkout claude/sign-language-translation-system-a0mzqi

# 의존성 (가상환경에 torch는 이미 있음 — 재설치하면 CUDA 버전이 깨진다)
pip install -r ml/requirements.txt

# GPU가 실제로 잡히는지 + 학습 루프가 도는지 (데이터 없이)
python -c "import torch; print(torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name(0))"
python -m ml.train_isolated --synthetic --epochs 3 --out <VOL>/runs/smoke
```

`--synthetic`은 **환경 점검 전용**이다. 여기서 나오는 정확도에는 아무 의미가 없다.
확인하려는 것은 "GPU·드라이버·학습 루프·체크포인트 저장이 이 워크스페이스에서 도는가"뿐이다.

### AI Hub 데이터 내려받기

AI Hub는 `aihubshell` CLI로 받는다(사이트에서 발급한 계정 필요).

```bash
cd <RAW_VOL>        # sbraw의 실제 마운트 경로
# aihubshell 설치 안내는 AI Hub 사이트 참조
aihubshell -mode l -datasetkey <데이터셋키>     # 파일 목록 확인
aihubshell -mode d -datasetkey <데이터셋키> -filekey <파일키>
```

> ⚠️ **연구망 egress 정책을 먼저 확인할 것.** KOREN 워크스페이스에서 외부 다운로드가
> 막혀 있을 수 있다. 첫날에 작은 파일 하나로 반드시 시험해 보고, 막혀 있다면 플랫폼의
> **데이터셋 등록** 기능이나 볼륨 업로드 경로를 쓴다. (이걸 나중에 발견하면 일정이 통째로 밀린다.)

## 4. 잡 스케줄링으로 장시간 학습 돌리기

노트북 셸에서 직접 돌리면 세션이 끊길 때 학습도 죽는다. 60에폭 학습은 **잡**으로 넣는다.
`ml/jobs/`에 진입 스크립트가 준비돼 있다.

```bash
bash ml/jobs/etl_mediapipe.sh      # CPU 워크스페이스에서
bash ml/jobs/train_isolated.sh     # GPU 워크스페이스에서
bash ml/jobs/train_ctc.sh
```

각 스크립트는 로그를 볼륨에 남기므로(`$RUNS_ROOT/<이름>/`), 세션이 끊겨도 진행 상황을
나중에 확인할 수 있다. 플랫폼의 **잡 스케줄링** 메뉴에 등록할 때도 이 스크립트를 그대로 쓰면 된다.

## 5. 플랫폼 기능 활용

좌측 메뉴의 기능들을 이 프로젝트에 이렇게 대응시키면 된다.

| 메뉴 | 활용 |
|---|---|
| **볼륨** | 위 3개 볼륨 생성·공유 |
| **데이터셋** | 팩 디렉터리(sbdata)를 데이터셋으로 등록 → 워크스페이스 간 재사용 |
| **잡 스케줄링 / 스케줄** | 장시간 학습, 야간 배치 |
| **자원 요청 / 결재함** | CPU 자원·볼륨·추가 GPU 신청 및 승인 확인 |
| **모니터링** | GPU 사용률 확인. **사용률이 낮으면 데이터로더 병목**이니 `--workers`를 올린다 |
| **모델/에이전트 · 모델 배포** | 학습된 모델을 추론 엔드포인트로 서빙(브라우저 대신 서버 추론을 쓸 경우) |
| **어노테이션/라벨링** | 자체 수집 수어 영상에 글로스를 붙일 때. AI Hub 어휘 밖 단어 보강용 |
| **파인튜닝 · RAG · 프롬프트셋** | Q&A 백본(현재 KoGPT2)을 상위 모델로 올릴 때 |

> **모니터링을 습관적으로 볼 것.** MIG 슬라이스에서 GPU 사용률이 30%대에 머문다면
> 십중팔구 모델이 작은 게 아니라 **CPU 데이터로더가 못 따라가는 것**이다.
> `--workers`를 늘리고 `--cache-size`를 조정하면 몇 배 빨라진다.

## 6. 자주 만나는 문제

| 증상 | 원인 / 대응 |
|---|---|
| 검증 정확도는 높은데 웹캠에서 안 됨 | 학습·추론 특징 불일치. `python -m ml.tools.feature_parity` 실행 |
| `CUDA out of memory` | MIG는 35GB지만 배치가 과할 수 있다. `--batch-size` 절반으로 |
| GPU 사용률이 낮음 | 데이터로더 병목. `--workers` ↑ |
| CTC 손실이 발산/NaN | 입력이 라벨보다 짧은 표본. `--conv-stride 1` 또는 `--max-frames` ↑ (스크립트가 건너뛴 개수를 보고한다) |
| 학습은 되는데 어휘가 20개도 안 됨 | `prepare.py --min-count` 를 낮추거나 데이터를 더 넣을 것 |
| 재시작하니 체크포인트가 사라짐 | `--out`이 볼륨 밖(홈)이었다. 데이터 볼륨 경로로 줄 것 |
| ONNX 내보내기가 BatchNorm에서 실패 | torch 2.5.x의 알려진 문제. **이미 해결됨**(프런트엔드가 LayerNorm). 옛 체크포인트를 쓰고 있다면 재학습 필요 |
| `Dim.DYNAMIC` AttributeError | torch 2.6부터의 API. **이미 해결됨**(2.5.x에서는 `Dim.AUTO` 자동 사용) |
| MediaPipe 추출이 너무 느림 | `--every 2`로 프레임 절반만(30fps → 15fps). 수어 인식에는 대개 충분 |

## 7. 첫 2주 제안 일정

| 시점 | 할 일 | 산출물 |
|---|---|---|
| D+1 | 볼륨 구성, 워크스페이스 2개, `--synthetic` 점검, **다운로드 가능 여부 확인** | 환경 완료 |
| D+2~4 | 재난 수어 데이터 수신 → `inspect_json`으로 스키마 확인 → ETL | `index.jsonl`, `vocab.json` |
| D+5 | `prepare` + 통계 확인(어휘 수·표본 수가 충분한가) | `stats.json` |
| D+6~8 | 단어 인식 학습·튜닝 | 첫 **수어자 분리 정확도** |
| D+9~10 | ONNX 내보내기 → 브라우저 연동 | 실제 동작하는 실시간 자막 |
| D+11~14 | CTC + 글로스↔한국어 | 문장 단위 데모 |

D+5의 `stats.json`이 첫 분기점이다. **어휘 수와 어휘당 표본 수**를 보고
목표 어휘 규모를 현실적으로 재조정할 것 — 여기서 무리하면 뒤가 전부 어긋난다.
